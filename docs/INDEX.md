# Pluris Documentation Index

**What:** The map of all Pluris documentation — start here. Every doc is one concept; wiki-links use file base names (Obsidian-compatible).

## How to use this brain
- **New here (human or AI)?** Read [[pluris]] → [[endpoint-management]] → the concept doc for whatever you touch.
- **Working on code?** `AGENTS.md` (repo root) has the hard rules; [[workflow]] has the process; [[handoff]] has the current state.
- **Strict-structure rule:** every doc lives in exactly one place in this tree and appears in this index. No stray files.

## Tree

- **product/** — what Pluris is
  - [[pluris]] — the product family: Endpoint Management + ITSM + OS, and how they interconnect
  - [[endpoint-management]] — the current product: charter, built features, honest gaps
  - [[itsm]] — planned: tickets, incidents, self-service portal
  - [[os]] — under consideration: managed Linux OS image
  - [[roadmap]] — shipped milestones and what's next
- **endpoint-management/** — technical docs for the current product
  - **architecture/**
    - [[overview]] — stack, repo layout, request flow, catalog-registry pattern, codegen
    - [[decisions]] — decision log (ADRs, condensed, with superseded markers)
    - [[data-model]] — every table by domain, migration discipline, sqlc conventions
  - **concepts/**
    - [[parameters]] — canonical parameter paths: the registry that drives detail pages, lists, filters, conditions, and field validation
    - [[authorization]] — Pluris Policy: console zero-trust permissions, role inheritance, group roles, enforcement layers, security notes
    - [[endpoint-policy]] — device policy: catalog with Windows GP mappings, configuration groups, dependency groups, policy modules (mock-vs-DB map)
    - [[identity-assets]] — the directory model: users (AD attribute parity), assets, groups, create/edit flows, field API
  - **ui/**
    - [[invariants]] — the formal UI contract (INV-ids): single sources of truth, DetailShell, list registry, testids
    - [[layout-system]] — the building blocks: layouts, heroes, tabs, toolbars, inline edit, pickers
  - **windows-admins/** — orientation for admins coming from AD/Intune (partly auto-generated by `cmd/gendocs`)
    - `windows-admins/README.md` (generated index) · [[concepts]] · [[cheatsheet]] · [[glossary]]
  - **examples/** — `examples/policy-modules/README.md` — a complete example policy-module bundle
- **development/** — how we build
  - [[setup]] — dev environment, make targets, running the console, the :8081 testing convention
  - [[testing]] — test conventions: scratch DBs, session injection, smoke tests, e2e pattern
  - [[workflow]] — spec→plan→subagent process, small-model session rules, strict-docs rule
  - [[handoff]] — living current-state doc: shipped, in-flight, caveats, next
- **history/** — immutable records (specs and plans as they were written; newest = closest to current truth)
  - `history/specs/` — design specs by date
  - `history/plans/` — implementation plans by date
  - `history/research/` — early research notes (fork strategy, platform landscape), superseded by [[decisions]]
- **funding/** — owner-private (gitignored), not part of this tree

## Relations (the cross-links that matter)
- [[parameters]] is the deepest dependency: [[invariants]] (INV-CPP/INV-L), [[identity-assets]] (field validation), [[endpoint-policy]] (dependency-group conditions) all build on it.
- [[authorization]] gates everything: [[layout-system]] menu/route gating, [[identity-assets]] field API scoping, [[endpoint-policy]] management surfaces. ITSM ([[itsm]]) will add its own permission domain here.
- [[endpoint-policy]] and [[authorization]] both say "policy" — the disambiguation callout lives at the top of [[endpoint-policy]].
- [[data-model]] ↔ [[decisions]]: every schema choice traces to a decision entry.
- [[handoff]] is the only doc that changes every session; history/ never changes.
